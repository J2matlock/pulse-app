# R2: Stale state across views and stores

Read-only review, 2026-10-11. Every item below was traced end to end in the code.

- **[bug]** `src/renderer/views/ProfileView.tsx:126-135` (with the lookup effect at `:157-179`): the `?gridId=` effect forces the active list back to the URL's list whenever `activeGridId` changes. To reproduce, open a record from the Dashboard (`/profile/42?gridId=5`) and choose ⋯ → Move to another list (7). `onDone` reloads list 5, so the record is no longer in `rows`. The lookup effect finds it in 7 and calls `loadGrid(7)`. The param effect then calls `loadGrid(5)`, which wins the `_loadVersion` check, and the `isLoading` change cancels the lookup (`live=false`). When list 5 finishes loading, the cycle starts again. The page shows "Loading…" forever while the two lists reload back and forth. The same loop happens when a Recent entry's stored `gridId` is out of date because the record was moved. **Fix:** apply the param once per `rowId` (keep the applied param in a ref), or skip it once the lookup has found the record somewhere else.
- **[bug]** `src/renderer/views/dashboard/TaskRow.tsx:59` and `src/renderer/views/FocusModeView.tsx:321`: the Undo on the "Completed task" toast calls `mustInvoke(IPC.TASK_RESTORE, task.id)` with a number. Main expects a full task object and returns "Invalid task format". It is also the wrong operation: TASK_RESTORE re-inserts a deleted task and refuses ids that still exist. The undo always fails, and because `undoStore.undo` puts a failed item back on top (`undoStore.ts:217-221`), Ctrl+Z gets stuck on it. `completeTask` already pushes a working TASK_UNCOMPLETE undo, so this is also a second undo step for the same action. **Fix:** remove the extra `pushWithToast` and use `pushWithToast` inside `completeTask`, or call TASK_UNCOMPLETE with the earlier values.
- **[bug]** `src/renderer/components/grid/ImportWizard.tsx:177,413,422` (`onImported` only runs at `:1061`): once an import has finished (step 6), closing the wizard with ✕, Esc or a click on the backdrop skips `onImported`. The open list is never reloaded (`GridToolbar.tsx:754-758`), so the imported records don't show and it looks as if the import failed. People then import again. **Fix:** call `onImported(importResult)` from every close path when `importResult` is set, for example in a wrapped `onClose`.
- **[bug]** `src/renderer/views/template-manager/ApplyTemplateDialog.tsx:58` and `src/renderer/components/shared/ImportPreviewModal.tsx:99`: applying a .pulse template creates alert rules (`templates.ts:441` `importAlertRules`), and in "existing" mode it also adds columns to that list. Only `loadGridList()` runs afterwards. `useAlertStore` is only reloaded when `!isLoaded`, so the new columns have no deadline colors and deadline-type cells show "Choose a deadline rule". When the target is the open list, the new columns don't appear at all. **Fix:** after applying, call `useAlertStore.getState().loadRules()`, and `loadGrid(id)` when the target is the active list.
- **[bug]** `src/renderer/components/settings/DataSection.tsx:31-39` (Add sample list) and `src/renderer/components/shared/SampleDataBanner.tsx:73-92` (Remove sample data): `createSampleCaseload` and `removeSampleCaseload` add and remove alert rules, tasks and providers (`sample-data.ts:165,234,239`), but the renderer only refreshes the grid list. Two effects:
  - After Add, the sample list's Last Contact and Annual Review columns have no colors until restart, because their rules aren't in `useAlertStore`.
  - After Remove, the deleted "Sample: …" rules stay in Settings → Deadline rules and in the column rule pickers, and the sidebar Tasks badge (`Sidebar.tsx:316`, loaded only while the task list is empty) keeps counting the deleted sample tasks.

  **Fix:** in both paths, also call `loadRules()` and `useTaskStore.getState().loadTasks()`, or have those stores listen for `sample-data:changed`.
- **[visible]** `src/renderer/components/starters/ApplyStarterDialog.tsx:125` together with `src/main/starters.ts:404,449-455`: many starters give their lists their own words. For example, Auto service's Vehicles list uses "vehicle". Those words live in `grids.vocab` and reach the window only through `workspaceStore.gridVocab`. In 'add' mode, "Use this example's words" is unticked by default, so `workspaceChanged` stays false, no WORKSPACE_CHANGED is sent, and the dialog never reloads the workspace store. The new lists show the workspace words ("Add client" in Vehicles) until the next workspace reload. **Fix:** always call `useWorkspaceStore.getState().load()` after an apply, or set `workspaceChanged` whenever a list with its own words was added.
- **[bug]** `src/renderer/components/starters/ApplyStarterDialog.tsx:125` and `src/renderer/hooks/useAuthGating.ts:99-108`: starters create link types (`starters.ts:441` `setupLink`), but `useLinkStore` only loads once (`isLoaded`). If any link cell or record page with links was opened earlier in the session, then after adding an example with links (sidebar, Settings → Workspace, or setup reopened after the last list was deleted):
  - `GridLinkEditor` returns null (`LinkPicker.tsx:166`), so editing a link cell does nothing.
  - The record page hides the linked-records section (`ProfileView.tsx:146,543`).

  **Fix:** call `useLinkStore.getState().load()` (or reset `isLoaded`) after a starter is applied and in `finishSetup`.
- **[visible]** `src/renderer/views/DashboardView.tsx:173-200`: the dashboard loads once when it mounts and only listens for `deadline:changed` and `followup:changed`. Two controls that are always on screen change its data without remounting it:
  - The sample banner's "Remove sample data" (MainLayout) leaves the sample records' deadlines, tasks and follow-ups on the dashboard.
  - Deleting a list from the sidebar ⋯ menu while on the Dashboard (`Sidebar.tsx:420-425`; `navigate('/dashboard')` does nothing there) leaves the deleted list's deadlines; clicking one gives "was on a list that has been deleted".

  The empty dashboard's "See an example with sample data" button has the same gap: after adding an example and closing the dialog without pressing Open, it still says "Nothing here yet". **Fix:** have the dashboard call `reload()` on `sample-data:changed` and on a new lists-changed event emitted by deleteGrid, restore and starter apply.
- **[visible]** `src/renderer/views/TrashView.tsx:54-64` and `src/renderer/views/dashboard/RecentlyArchivedTab.tsx:25` (with `DashboardView.tsx:682`): restoring a record from the Trash, or reactivating one from Dashboard → Recently archived, writes over IPC without touching `useGridStore`. GridView reloads only when nothing is loaded or nothing is selected (`GridView.tsx:84-106`). Going back to the list through the breadcrumb (`TopBar.tsx:156`), Back, or the Getting started links shows the old rows without the restored record. Reactivating also doesn't reload the dashboard's priority list or counts. **Fix:** after a successful restore or reactivate, call `loadGrid(activeGridId)` when the record belongs to the open list, and call the dashboard's `reload()`.
- **[visible]** `src/renderer/components/settings/AlertsSection.tsx:34-36,76`: the "Used by: …" line under each deadline rule comes from `alertStore.usage`, which is only refreshed by `loadRules()`. In this section that runs only when `!isLoaded`, normally once at unlock. Giving a column a rule, deleting a column or deleting a list doesn't refresh it, so a rule that was just assigned still says "Used by: no columns yet". **Fix:** call `loadUsage()` when AlertsSection mounts.
- **[bug]** `src/renderer/views/TrashView.tsx:76-80,92-99` together with `src/renderer/stores/undoStore.ts:217-221`: if you delete a list (its undo is "restore"), then use "Delete forever" or "Empty Trash" in the Trash, the undo step stays on the stack. Ctrl+Z then fails with "That list is no longer in the Trash", the failed item is put back on top, and every later Ctrl+Z hits the same error, so nothing earlier can be undone. Rows deleted and then purged behave the same way. **Fix:** clear the undo stack, or drop matching items, after a purge or Empty Trash. In addition, `undo()` could drop an item whose target is gone instead of putting it back.
- **[polish]** `src/renderer/stores/profileStore.ts:33`: `clearRecentProfiles` is never called (dead code), and recent entries are never pruned or renamed. After records are trashed, sample data is removed, a list is deleted or a record is renamed, the TopBar Recent menu and the palette's Recent list keep old names, which lead to "This record is in the Trash". Their stored `gridId` also triggers the ProfileView loop described above once a record is moved. **Fix:** prune entries on `sample-data:changed`, deleteGrid and deleteRow, update the name on rename, and stop passing the stored `gridId` (let ROW_LOCATE find the list).
- **[polish]** `src/renderer/components/layout/Sidebar.tsx:316-322`: `todayDueCount` is a `useMemo` over `[tasks]` that reads `localDateString()`. If Pulse stays open (or locked) past midnight, the Tasks badge doesn't count tasks that became due until the task list changes. **Fix:** add the current day as a dependency, for example from a once-a-minute tick or a date key that updates on focus or unlock.
