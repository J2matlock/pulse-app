# R5: setup, starters, settings, import/export, backup

Reviewer R5, 2026-10-11. Each item below was checked by reading the code path from end to end.

## Bugs

- **[bug]** `src/renderer/views/SetupView.tsx:170-176`, `src/renderer/components/grid/ImportWizard.tsx:177,413,422`: during first-run setup, "Bring in a spreadsheet" can throw away a finished import.
  - What goes wrong: on the import results screen, Escape, the ✕ button and a click on the backdrop all call `onClose` without `onImported`. Only "Done" calls `onImported`. In setup `onClose` is `cancelImport`, and `importDone.current` is still false at that point, so it runs `GRID_DELETE`. The list the user just imported into (for example 200 records) goes to the Trash and setup goes back to "Name the list". Nothing tells the user what happened.
  - Second path: "Undo this import" followed by "Done" still calls `onImported`. Setup then asks "What are these rows?" about a list that is now empty.
  - Fix: once `importResult` is set, the close paths (✕, Escape, backdrop) should call `onImported(importResult)` the same way Done does. Or `cancelImport` could check a flag the wizard sets as soon as the import succeeds. If the undo left 0 rows, `onImported` should not be called (or setup should treat the list as empty).

- **[bug]** `src/main/sample-data.ts:143-149` with `src/renderer/components/shared/SampleDataBanner.tsx:93,120`: "Remove sample data" says the sample list's entries go to the Trash, but they are deleted for good.
  - What goes wrong: for the sample caseload (Settings → Data → Add sample list), `removeSampleData` first moves the untouched rows to the Trash. `removeSampleCaseload` then finds `theirs === 0` and runs `DELETE FROM grids`, which cascades and hard-deletes those same rows, with their notes and history.
  - The dialog says "25 made-up … will move to the Trash. You can bring them back from there for 30 days" and the toast says "moved to the Trash". The Trash is empty.
  - Fix: either move the whole sample list to the Trash with `trashList`, so the promise holds, or have the preview and the result report "the sample list and its N entries will be deleted" in this case.

- **[bug]** `src/main/backup.ts:920,968` with `src/main/ipc/ipc-export.ts:107-111,139-145`: a failed restore leaves the database closed.
  - What goes wrong: `restoreFromDb` and `restoreFromPulseBackup` close the database before copying or extracting. If they throw (zip error, extract failure, copy failure, too big), they copy the safety file back but never reopen the database. The handler's `openDatabase()` only runs on success.
  - Result: the renderer shows "Restore failed. Please try a different backup." and the user carries on. Every later action fails with "Database is not open. Please unlock the app first." until a lock or a restart.
  - Fix: in both handlers, wrap the restore call in try/catch and call `openDatabase()` before returning `fail`, as `BACKUP_RESTORE_OTHER` already does (`ipc-export.ts:186-189`).

- **[bug]** `src/main/export-supervisor.ts:229-233,510-514`: the summary report's task section leaves out tasks completed on the end date, and the end date defaults to today.
  - What goes wrong: the query uses `completed_at < dateRange.end`. `completed_at` is an ISO timestamp (`2026-10-11T15:00:00.000Z`) and `end` is `2026-10-11`. In string comparison, `'2026-10-11T…' < '2026-10-11'` is false. With the default end of today (`SupervisorReportDialog.tsx:75`), nothing finished today appears.
  - Related, in the same report: "new", "archived" and "removed" use `date(created_at|archived_at|deleted_at)` without `'localtime'` (lines 48, 53, 60, 95, 262), and line 236 uses `completed_at.slice(0, 10)`. Both give UTC days, so evening entries land on the next day or month. The activity log in the same report does use `'localtime'`.
  - Fix: compare with `date(completed_at, 'localtime') BETWEEN ? AND ?` and add `'localtime'` to the other `date()` calls.

- **[bug]** `src/main/export-supervisor.ts:242-247,548-555`: the summary report's activity log includes notes it shouldn't, and can include raw HTML.
  - Voided (struck-out) notes are included: there is no `voided_at IS NULL` filter.
  - Notes on records in the Trash are included: there is no `r.deleted_at IS NULL` filter.
  - `content` is printed without `stripHtml`, unlike every other export (`export-pdf.ts:298`, `export-csv.ts:81`, `export-audit.ts:131`).
  - Fix: add `cl.voided_at IS NULL AND r.deleted_at IS NULL` to both queries and pass `stripHtml(e.content)` to both outputs.

- **[bug]** `src/main/export-csv.ts:67-82`: Export everything → `notes.csv` dates each note by `created_at` (when it was typed), not `occurred_at`. Under Decision B1, a note backdated to Sept 30 and written Oct 2 is exported as Oct 2, while the PDFs and the summary report use `occurred_at`.
  - Fix: select and order by `cl.occurred_at`. Optionally add a "Written" column for `created_at`.

## Visible

- **[visible]** `src/renderer/components/grid/GridToolbar.tsx:750-758`, `src/renderer/components/settings/DataSection.tsx:171-176`: the list goes stale after an import or an undone import. This is the same close-path gap as the first bug. Closing the results screen with ✕ or Escape, or by clicking outside, skips `onImported`, so the list isn't reloaded. Imported records don't show, or records the import undo moved to the Trash stay on screen, until the user goes to another page. Fix: one change in ImportWizard (call `onImported` from every close once there is a result) fixes all three callers.

- **[visible]** `src/main/sample-data.ts:69-71,85-86` with `src/renderer/components/shared/SampleDataBanner.tsx:143-153`: deleting the sample list leaves a sample-data banner on screen.
  - With Decision D1, deleting a list only sets `grids.is_active = 0`, and its rows keep `deleted_at IS NULL`. `countSampleRows` and `planSampleRemoval` don't check `grids.is_active`, so the rows of a list in the Trash still count as live samples.
  - Nothing emits `sample-data:changed` when a list or a row goes to the Trash or comes back. The banner keeps saying "You're exploring a sample list". After the next refresh it switches to "… with a sparkle are made-up samples", though none are visible.
  - Fix: join `grids g ON g.is_active = 1` in both queries, and emit `sample-data:changed` after a list delete or restore and after a row trash or restore.

- **[visible]** `src/renderer/views/SetupView.tsx:172`: cancelling the spreadsheet import in setup sends the empty list it made ("My list") to the Trash, because `GRID_DELETE` now trashes lists (D1). Each Back → "Choose file" → cancel adds another "My list" to the Trash, which the user never knowingly made. Fix: purge the never-used list (`GRID_PURGE` after the delete, or a delete-if-empty call) instead of trashing it.

## Polish

- **[polish]** `src/renderer/components/settings/DataSection.tsx:249`: "Compacted: 340 records removed." In a workspace where the record word is "client", this reads as if clients were deleted. Fix: "Removed 340 old cell changes from the history."

- **[polish]** `src/main/ipc/ipc-auth.ts:124-131`, `src/main/ipc/ipc-export.ts:186-193`, `src/main/backup.ts:1213`: both restore-with-password paths (first run and "backup from another Pulse") return the raw error with `fail(msg)` and skip `humanizeError`. Users can see:
  - "Database file hash mismatch — backup may be corrupted"
  - the zip library's "end of central directory record signature not found"
  - SQLite's "file is not a database"

- **[polish]** `src/renderer/components/settings/BackupSection.tsx:322`, `src/main/backup.ts:414`, `src/main/index.ts:396`: when an automatic backup fails, the stored message is the raw `err.message` (for example "ENOSPC: no space left on device, copyfile '/home/…'"), and Settings shows it word for word. Fix: store `describeBackupError(err)`, which already exists, instead.

- **[polish]** `src/renderer/components/grid/ImportWizard.tsx:82-89,193,365,787`, `src/main/import.ts:1032,1081`: the import wizard still shows developer text.
  - Step labels: "Column Mapping", "Select File".

  - A chunk failure puts the SQLite text in a warning: "Import stopped at row 52: UNIQUE constraint failed…".

The most common cause on Windows is the CSV still being open in Excel; `humanizeError` maps that to a permission message. Fix: `toast.error(friendlyError(result.error, 'Export failed…'))`.
