# S4: main-process data integrity

Reviewer S4, 2026-10-11. Each item below was checked by reading the code path from start to finish. Already reported in polish R5 and left out here: the failed restore leaving the database closed, sample removal hard-deleting, and the supervisor report filters.

FK enforcement matches what the code assumes. `foreign_keys = ON` is set on every connection (`database.ts:224`), and every table added in 039–047 cascades from `rows`, `columns` and `grids` as the trash, restore and purge code expects. Attachments live in the encrypted database (`attachment_blobs`), so every backup layer carries them. The gaps are in JSON references, in-memory caches and a few counts.

## Bugs

- **[bug]** `src/main/ipc/ipc-export.ts:355` with `src/main/export-shared.ts:244`: "Export everything as CSV" leaves out every archived record.
  - What goes wrong: `exportCsv` → `loadGridData` calls `buildGridQuery(..., false)`, which adds `r.is_active = 1`.
  - Example: someone exporting before they leave the app, or to hand over a caseload, loses every discharged or closed client.
  - The `notes.csv` written next to it does include those records' notes (`export-csv.ts:71` filters only `deleted_at`), so it holds notes for people who aren't in any list file.
  - Fix: give `loadGridData` an `includeArchived` option and pass it from EXPORT_ALL_CSV. Optionally add a "Status" (Active/Archived) column.

- **[bug]** `src/main/templates.ts:258-285` (`exportGridAsPulse`), `templates.ts:520-567` and `starters.ts:412`: Age and Days-until columns still point at the old database's column id after a .pulse share or a "Save my setup" template.
  - What goes wrong: `age_from_dob` and `calculated_days` columns keep `config.source_column_id`, the id of the date-of-birth or date column in the database that made the file.
  - `exportConfig` turns rule and checklist ids into names but not this one. `applyPulseToNewGrid`, `applyPulseToExistingGrid` and `applyStarter` insert the config unchanged.
  - Result: on the colleague's computer, the Age column is blank for every record. It can also read a column of some other list that happens to have that id.
  - The same happens in one database: save a list as a template, apply it to a new list, and the new list's Age column points at the original list's DOB column, so it shows blank.
  - Fix: on export, write `source_column_name`. On apply, after inserting the columns, resolve it to the new list's column of that name (as `linkColumnRules` does for rules).

- **[bug]** `src/main/backup.ts:1186-1189` with `src/main/ipc/ipc-export.ts:197`: Settings → Restore a backup "from another Pulse" replaces the data and the password before checking that this Pulse can open the backup.
  - What goes wrong: `restoreBackupOnNewInstall` reads `info.schemaVersion` but never compares it with the newest migration. It moves the current database aside, installs the backup and rewrites the credentials with the new password (`adoptRestoredDbKey`).
  - Then `openDatabase()` at `ipc-export.ts:197` (outside any try) throws "created by a newer version of Pulse". The user gets a generic failure.
  - The live data is now the newer backup under a new password, and Pulse can't open it until the app is updated. The old data survives only as the pre-restore `.pulse-backup`, under the old password.
  - Example: an office PC restoring a backup made on a home PC that already updated.
  - Fix: in `restoreBackupOnNewInstall`, right after `readEncryptedDbInfo`, refuse when `info.schemaVersion` is newer than the latest migration: "This backup was made by a newer Pulse. Update Pulse first." This must happen before `moveAsideExistingDatabase` and `adoptRestoredDbKey`. Also wrap the handler's `openDatabase()` in try/catch with a plain message.

- **[bug]** `src/main/database.ts:128-133` with `src/main/ipc/ipc-cell.ts:19,44-45`: after a restore, cell saves can use stale column settings.
  - What goes wrong: every restore (`restoreFromDb`, `restoreFromPulseBackup`, `restoreOtherPulseBackup`) closes the database through the backup bridge. The bridge clears the statement cache but never runs the close hooks.
  - So `_colMetaCache` (column type, name and `log_changes`, keyed by column id) survives the restore, even though the comment at `ipc-cell.ts:44` says it's cleared on restore.
  - Restoring an older backup also rewinds `sqlite_sequence`, so the next new column reuses an id from the old session.
  - Example: add a link column, restore this morning's backup, then add a text column. The text column gets the same id, and typing in it fails with "That column shows links. Use the link picker to change it." A reused auto-number id fails with "Numbers are filled in automatically". A reused `log_changes` id writes change notes under the old column's name.
  - Fix: have the bridge's `closeDatabase` run `_closeHooks` (or at least `invalidateColumnCache()`), or call `invalidateColumnCache()` after each successful restore.

- **[bug]** `src/main/import.ts:880,1019,1026-1034`: when part of an import fails, the results screen reports more records than came in.
  - What goes wrong: `imported++`, `skipped++`, `skippedNames`, the truncation `warnings`, `unreadableDates` and `birthAs1900s` are all updated inside the chunk transaction. When a chunk throws, its rows roll back but the counters keep them.
  - Example: a 200-row file that fails at row 77 says "Imported 75" (or more), but only 50 rows (the first chunk) are in the list.
  - Fix: count into chunk-local variables and add them to the totals only after `insertChunk()` succeeds. Or recompute `imported` from `newRowIds.length`.

- **[bug]** `src/main/display-names.ts:29` with `src/main/ipc/ipc-grid.ts:265` (visibility) and `ipc-grid.ts:325-328` (delete): names go stale when a "Last name" column is hidden, shown or deleted.
  - What goes wrong: the default record name joins a "Last name" column only while `last_col.is_visible = 1`. But the display-name triggers fire only on cell writes and on column `name` / `is_name_column` changes.
  - Deleting such a column cascades its cells after the column row is gone, so `trg_display_name_delete`'s WHEN finds nothing. COLUMN_DELETE refreshes only when the deleted column was the name column or the list has a format.
  - Result: after hiding or deleting "Last name", the dashboard, search, links and record page keep showing "Jane Smith". The next edit to any first name turns that one record into "Jane", so names in the same list disagree.
  - Fix: in COLUMN_DELETE, COLUMN_UPDATE (`is_visible`) and COLUMN_BATCH_UPDATE_VISIBILITY, call `refreshDisplayNames(gridId)` when the column's name is one of the last-name names, or always when the list has no display format (it's one UPDATE).

## Visible

- **[visible]** `src/main/ipc/ipc-tasks.ts:21-33`: the Tasks page still shows tasks tied to a list in the Trash.
  - What goes wrong: TASK_GET_ALL has no `grids.is_active` check. TASK_GET_DUE, the briefing count (`ipc-dashboard.ts:107`), the calendar and the planner all hide these tasks with `ct.grid_id IS NULL OR g.is_active = 1`.
  - Result: after a list is deleted, its tasks stay on the Tasks page (with no list name, because the picker only knows active lists) but are missing from the dashboard and calendar. After 30 days they disappear without warning when the purge cascades them.
  - Fix: add `LEFT JOIN grids g ON g.id = ct.grid_id … AND (ct.grid_id IS NULL OR g.is_active = 1)` to both queries.

## Polish

- **[polish]** `src/main/sample-data.ts:168,180-186`: a sample list brought back from the Trash has no deadline rules.
  - What goes wrong: when "Remove sample data" moves the whole sample list to the Trash, the sample rules are then unlinked from its columns and deleted, because `inUse` only counts active lists.
  - Result: "you can bring them back for 30 days" brings back the records, but every deadline column is empty of deadlines. Sample tasks are hard-deleted too.
  - Fix: keep rules that a list in the Trash still uses (count `deleted_at IS NOT NULL` lists in `inUse`). The purge removes them later with the list, or they can be cleaned up when the list is purged.

- **[polish]** `src/main/backup.ts:878,926,1242`: `pulse-pre-restore-*` safety copies are never pruned.
  - Each restore leaves a full database copy in the backups folder for good. With files now stored in the database (up to 4 GB), a few restores can take many gigabytes.
  - Fix: `pruneBackups(dir, 'pulse-pre-restore-', …, 3)` after each restore, as is done for pre-migration copies.

- **[polish]** `src/main/ipc/ipc-export.ts:316`: the restore preview's record count includes records in lists that are in the Trash.
  - Deleted lists keep `rows.is_active = 1` under D1. `BACKUP_GET_INFO` already joins `grids g … g.is_active = 1` (X-11).
  - Fix: use the same join here.

- **[polish]** `src/main/column-options.ts:76`: renaming a choice with "update records" skips records in the Trash (`r.deleted_at IS NULL`).
  - Restoring one later gives a record whose value is no longer a choice, so it shows as an odd leftover and filters miss it.
  - Fix: include trashed records in the rename. It's the same value, just relabelled.

- **[polish]** `src/main/list-trash.ts:150,190`: the link history shows links as removed even after the list comes back.
  - Trashing a list writes a `remove` row in `record_link_history` for every link (through `deleteLinkType`). Restoring it puts the links back with no matching `add`, so "Show me the record" (export-audit) reports them as removed.
  - Fix: in `restoreList`, insert an `add` history row for each link it restores.
