# S2 — Tasks, checklists and recurrence

Read-only review, 2026-10-11. Every item below was traced through the code end to end.

## Bugs

- **[bug]** `src/shared/recurrence.ts:44-57` (used by `src/main/ipc/ipc-tasks.ts:138` and `src/main/ipc/ipc-checklists.ts:96`): monthly and yearly repeats drift to the end of the shortest month. When a monthly task due Jan 31 is ticked off, it becomes due Feb 28 and that date is saved. The next tick works from Feb 28, so it comes back due Mar 28, Apr 28, and so on for good. A yearly Feb 29 item becomes Feb 28 the same way. The "don't drift" loop only helps within a single roll-forward, not from one completion to the next. Fix: save the day of the month in the rule (e.g. `{"type":"monthly","interval":1,"day":31}`) when the rule is set, and have `addRepeats` clamp from that day, not from the current due date.

- **[bug]** `src/main/ipc/ipc-tasks.ts:130-144` + `src/main/export-supervisor.ts:229-233,509-513`: completing a repeating task doesn't show up anywhere. `TASK_COMPLETE` writes the completion only to `caseload_task_history`, and nothing reads that table. The task goes back to `is_completed = 0`, so a weekly task done 4 times this month isn't in the supervisor report's "Task Summary — Completed This Period" (which reads `caseload_tasks.is_completed = 1`). It also never appears in the Tasks page's Completed list or progress bar. Fix: have the supervisor report (and, if wanted, the Completed section) union in `caseload_task_history` rows for the period.

- **[bug]** `src/renderer/components/profile/Checklist.tsx:401-407, 446-462, 494-502`: the record page's checklist has the stale-id undo/redo bugs that TasksView already fixed.
  - Add group → Undo → Redo → Undo: the group stays, because redo makes a new id and undo still deletes `created.id`.
  - Delete group → Undo → Redo: redo deletes the old `groupId`, which no longer exists, so the recreated group stays.
  - Apply template into a new group → Undo → Redo: redo re-applies into the deleted `createdGroupId`. The items get a `group_id` with no group behind it, so they're invisible whenever the record has other groups. A second Undo then deletes the old `createdIds` and leaves the new items in place.

  Fix: track the current ids in `let` variables updated by redo, the same way `TasksView.handleAddGroup`/`applyTaskTemplate` do.

- **[bug]** `src/main/ipc/ipc-tasks.ts:180-202` (with `taskStore.ts:79,133`): `TASK_RESTORE` puts back a stale `group_id` without checking it, and `caseload_tasks.group_id` has no foreign key. Scenario: delete task T in group G, delete group G, then Undo twice. The group comes back under a new id, and T is restored pointing at the old G. In My order with groups, `groupedActiveTasks` puts T under a key that is never rendered. T is invisible but still counted in "N active" and the progress bar. The same happens after create → delete group → undo → undo → redo. Fix: in `TASK_RESTORE` (and `CHECKLIST_RESTORE_ITEM`), set `group_id` to NULL when the group no longer exists. As a safety net, render tasks with an unknown group as ungrouped.

- **[bug]** `src/renderer/views/TasksView.tsx:384-411` (and the same handler at `Checklist.tsx:290-320`): dragging between groups doesn't work, and reordering groups mostly fails.
  - Group headers and tasks share one `DndContext` with `closestCenter`. When you drag a group header past an expanded group, it usually lands on a task, the `group-`/`group-` check fails, the item branch finds no index, and nothing happens.
  - Dropping a task on a task in another group runs `arrayMove` over every group's tasks at once and calls `reorderTasks` without changing `group_id`. The task snaps back to its own group, and its order *inside* that group changes. Example: A=[a1,a2], B=[b1,b2]; drag a1 onto b2, and group A now reads a2, a1.

  Fix: when `over` is in another group (or is a group header), call `TASK_MOVE_TO_GROUP` and reorder only that group. Use a collision check that only considers group headers while a header is being dragged.

- **[bug]** `src/renderer/components/tasks/TaskItem.tsx:192-207` and `src/renderer/components/profile/ChecklistItem.tsx:344-361`: the "Clear date" ✕ button can't be clicked. Pressing the mouse (or Tab) on it blurs the date input first. `onBlur={saveDate}` runs `setEditingDate(false)`, which React flushes right away for a discrete event, so the ✕ is gone before the click lands. Fix: on the ✕ use `onMouseDown={e => e.preventDefault()}` (or check `relatedTarget` in the blur handler) so the input stays focused until the click.

- **[bug]** `src/main/ipc/ipc-tasks.ts:21-33` vs `:35-49`, `ipc-dashboard.ts:106-112`, `calendar.ts:32`: tasks linked to a list in the Trash disagree across screens. The Tasks page (`TASK_GET_ALL`, no `grids.is_active` filter) still shows them and counts them as overdue. The Dashboard, briefing and calendar hide them. When the Trash is emptied, `ON DELETE CASCADE` deletes those tasks without a word. The urgent-items query has the opposite gap: `ipc-checklists.ts:147` (`CHECKLIST_GET_URGENT`) joins `grids` without `g.is_active = 1`. Urgent checklist items from records in a trashed list stay on the Tasks page, and the link opens a record in a deleted list. Fix: apply the same `(grid_id IS NULL OR g.is_active = 1)` filter in `TASK_GET_ALL` and add `AND g.is_active = 1` to the urgent query (or show both everywhere with a "list is in the Trash" tag).

- **[bug]** `src/renderer/components/layout/Sidebar.tsx:334-340`: the sidebar's "due today or late" task badge doesn't leave out snoozed tasks (`snoozed_until > today`), and it counts tasks in trashed lists. The Tasks page overdue count, the Dashboard and the briefing all leave snoozed tasks out. Snoozing an overdue task leaves the badge unchanged. Fix: filter with `!isSnoozed(t)` from `views/tasks/taskHelpers`.

## Visible

- **[visible]** `src/renderer/views/dashboard/TaskRow.tsx:40-42`: an Urgent task gets the same white ⚪ dot as a Low one. The mapping only knows high → 🔴 and normal → 🟡. `ChecklistDueRow.tsx:43-45` treats urgent as red. Fix: `task.priority === 'high' || task.priority === 'urgent' ? '🔴'`.

- **[visible]** `src/renderer/views/TasksView.tsx:141-149` (and `DashboardView.tsx:582-584,647-649`): when you tick a *repeating* urgent checklist item on the Tasks page, it disappears from "Urgent checklist items" and the header's "· N urgent" count drops. Main has already moved it to its next due date and it's still open and urgent, so it comes back only on the next visit. The Dashboard's checklist rows do the same for a repeating item whose next date is inside the window. Fix: after `tickChecklistItem` succeeds, call `loadUrgentItems()` (Dashboard: reload `CHECKLIST_GET_DUE`), or put the item back with `repeat.nextDue` when one is returned.

- **[visible]** `src/renderer/components/shared/GroupHeader.tsx:69-75`: any group still called "New Group" opens in rename mode, with the text selected and focus taken, every time it mounts. That's every visit to Tasks, every switch back to My order, and every record page with such a checklist group. With two un-renamed groups, both open. Fix: have the parent pass an `autoEdit` flag only for the group it just created, instead of matching on the name.

- **[visible]** `src/main/ipc/ipc-tasks.ts:294-328`: "Apply template" on the Tasks page ignores the template's "Repeats every N days" setting. `TASK_APPLY_TEMPLATE` never reads `is_recurring`/`recurrence_days`, while the same template on a record page makes repeating items (`checklist-apply.ts:26-27`). Fix: when the template repeats, set `recurrence_rule = {"type":"daily","interval":N}` and `due_date = today` on the tasks it creates. Also check that each item's `priority` is in `ALLOWED_PRIORITIES`.

## Polish

- **[polish]** `src/main/ipc/ipc-tasks.ts:141` + `src/renderer/stores/taskStore.ts:191-195`: ticking off a snoozed *repeating* task clears `snoozed_until`, and undo (`TASK_UNCOMPLETE`) doesn't restore it, so the snooze is lost. Fix: include `snoozed_until` in the undo snapshot and in `TASK_UNCOMPLETE`.

- **[polish]** `src/renderer/stores/taskStore.ts:84-86,93,123,216` + `TasksView.tsx:629-631,743-745`: `createTask`/`updateTask`/`deleteTask`/`snoozeTask` swallow business errors without telling the user. Only read-only gets a toast. The inline "+ Add task" box is cleared either way, so a failed add (for example a pasted title over 500 characters, since the title inputs have no `maxLength`) loses the text silently. Fix: toast a plain-English error in the catch blocks and clear the input only when `createTask` returns a task.

- **[polish]** `src/renderer/components/tasks/TaskItem.tsx:86-90`: opening the date editor and clicking away without changing anything still sends `TASK_UPDATE` and pushes an "Updated task" undo step that does nothing. Fix: skip `onUpdate` when `dateDraft === (task.due_date ?? '')`.

- **[polish]** `src/renderer/views/TasksView.tsx:262-266,284-290`: group rename and group delete ignore the `safeInvoke` result. They update the screen and push an undo step even when the write failed. Fix: check `res.ok`, and toast and stop when it's false.
