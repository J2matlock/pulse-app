# S5 — Dates and time

Checked with the machine's own zone (America/New_York, EDT). Every item below was traced end to end.

- **[bug]** `src/main/import.ts:434` — Every real Excel date cell comes in **one day early** for anyone west of UTC (all US users). ExcelJS turns a date serial into a JS Date at **UTC** midnight (`utils.excelToDate`: `new Date((v - 25569) * 86400000)`), but `excelCellToString` reads it with local getters (`getFullYear/getMonth/getDate`). Example: a cell showing 3/15/2026 becomes `2026-03-15T00:00Z`, which is Mar 14 at 8 pm EDT, so it's stored as `2026-03-14`. Every DOB, review date and deadline imported from .xlsx is off by a day, and no test covers a real date cell. — Use `getUTCFullYear/getUTCMonth/getUTCDate` (the Date is a UTC-midnight stand-in for a calendar day). Add an import test that writes a date cell with ExcelJS.

- **[bug]** `src/main/import.ts:446` — Formula cells that work out to a date (e.g. `=A2+90`, `=EDATE(B2,6)`, `=TODAY()` formatted as a date) come back from ExcelJS as `{ formula, result: Date }`, and `String(result)` turns that into `"Sat Mar 14 2026 20:00:00 GMT-0400 (Eastern Daylight Time)"`. `parseDate` can't read that, so the column isn't detected as a date, and the long text gets imported or counted as unreadable. — In this branch, when `result instanceof Date`, format it with the same UTC-getter YYYY-MM-DD as the fix above.

- **[bug]** `src/main/import.ts:133` (with `detectColumnType` at :158) — `looksLikeDate` counts **any 5-digit number** from 1 to 73050 as an Excel serial, and the date check runs before the number check. So a Zip column (`60614`, `10001`, `02139`) or a 5-digit client/Medicaid ID column is detected as **Date**, and importing it as-is stores `2065-03-…`, `1927-05-…`, `1905-11-08`. — Only accept serials as dates when the cell was a real Excel date (the Date path above), or when the header names a date. Otherwise treat 5-digit numbers as numbers/text.

- **[bug]** `src/shared/parseDate.ts:23` — `fullYear` reads a two-digit year after the current year as 19xx: in 2026, `"1/15/27"` becomes **1927-01-15**. It's used by import and by pasting into the grid (`gridHelpers.validateForColumnType`). So typing or pasting next year's authorization end, lease end or review date with a short year makes it about 100 years overdue straight away. In December this hits nearly every date for the coming months. Birth-date columns are already pushed back a century in `executeImport` when they land in the future, so the aggressive pivot isn't needed there. — Use a forward window, like Excel (00–29 → 2000s) or current year + 20. Keep the existing birth-column "not in the future" correction, and apply it to grid paste into DOB-like columns too.

- **[bug]** `src/shared/recurrence.ts:44` (`nextRepeatDate`, used by `ipc-tasks.ts` TASK_COMPLETE and `ipc-checklists.ts`) — Repeating tasks and checklist items **drift at month ends**. The next date is counted from the *current* due date, and the rule doesn't remember the original day. Monthly from 2026-01-31: done → Feb 28, done → **Mar 28**, Apr 28… forever. Yearly from 2028-02-29: Feb 28 2029 … **Feb 28 2032** (should be Feb 29). The comment "so month-end dates don't drift" only holds within one completion. Appointment series don't have this problem; they count from the first start. — Store the anchor day in the rule JSON (e.g. `day: 31`, set when the repeat is first saved) and clamp `min(anchorDay, daysInMonth)` in `addRepeats`.

- **[bug]** `src/main/export-supervisor.ts:154` — The Summary report's period label parses `'YYYY-MM-DD'` with `new Date(dateRange.start)`, which reads it as UTC midnight, then formats it in local time. For any US user, "Oct 1 – Oct 31, 2026" prints as **"Sep 30, 2026 – Oct 30, 2026"** in both the CSV ("Period") and the PDF executive summary, while the counts use the right days. — Format with `ymdToDate(...)` / `formatDue(...)` (local parse), as the rest of the file does at line 534.

- **[bug]** `src/shared/cellText.ts:22` and `src/main/export-shared.ts:186` — **Age** (`age_from_dob`) and **Days until** (`calculated_days`) columns have no stored cells; the grid works them out from their source column. `cellText` returns the raw (null) value for them, so CSV/PDF export, batch print, the Summary report roster and copying a cell all show these columns **blank**. That breaks G-08's "exports show what the table shows". — Give `cellText`/`formatCellValue` the row (or fill computed values in `loadGridData`), using the same age and days-until math as `computeAge` / `report-builder.ageFrom`.

- **[bug]** `src/renderer/components/grid/CellConditionalFormatPanel.tsx:616` — The highlight-rules panel offers number comparisons for Age and Days-until columns (lines 73 and 334: "Greater than 65"). But `evalCellFormat` is passed the stored value, which is always null for these columns, so it hits `if (!value) continue` and the rule **never fires**. — For computed columns, pass the computed number (age, or days until) as `selfValue` in `SortableRow` / `GridContextMenu`.

- **[bug]** `src/renderer/components/grid/FilterBar.tsx:69` + `src/renderer/utils/filterMatch.ts:78` — Age and Days-until columns appear in the filter column picker with **text** operators, matched against the null stored value. "Age contains 6" matches no one, and "Age is empty" matches **every** record, even when everyone has an age. — Give these columns number operators (gt/lt/equals) and match against the computed value, or leave them out of the filter picker.

- **[bug]** `src/renderer/components/layout/Sidebar.tsx:334` — The Tasks badge counts tasks that are due today or late **including snoozed ones**. The Tasks page (`isSnoozed`), dashboard and briefing (`snoozed_until <= today`) all hide those. Snoozing an overdue task "until tomorrow" moves it out of the list, but the badge still says 1. — Add `&& !(t.snoozed_until && t.snoozed_until > today)` (or reuse `isSnoozed` / `isOverdue` / `isDueToday` from `taskHelpers`).

- **[visible]** `src/renderer/views/DashboardView.tsx:185`, `src/renderer/components/layout/Sidebar.tsx:334`, `src/renderer/views/dashboard/WeekViewTab.tsx:40`, grid `SortableRow` memo — Nothing in the renderer notices the date changing. There's no timer, no `visibilitychange` and no focus refresh. Dashboard data, `tasksWithDays` / `checklistWithDays` / `followUpsWithDays` memos, the sidebar badge and grid deadline colors are worked out once, when loaded or when data changes. With auto-lock set to Never (or someone working across midnight), at 00:01 everything still says "Due today" for yesterday's items and nothing turns overdue until a reload. The default 15-minute auto-lock hides this, because locking unmounts the app. — Add a small `useToday()` hook (a timeout set for the next local midnight, plus a check on window focus) that bumps a store value, and add it to these memos' dependencies and the dashboard's reload.

- **[polish]** `src/main/export-audit.ts:159` — Audit-trail events are sorted by string, but timestamps come in two formats: `datetime('now')` (`2026-10-11 15:00:00`) for notes, cells and records, and `toISOString()` (`2026-10-11T13:00:00.000Z`) for checklist `completed_at` (from `Checklist.tsx:167` / `checklistTick.ts:24`). `' '` sorts before `'T'`, so on the same UTC day a 13:00 checklist tick is listed **after** a 15:00 note. — Sort by `parseDbTimestamp(at).getTime()`, or store `completed_at` with `datetime('now')` format, as tasks' history should too.

- **[polish]** `src/renderer/components/grid/SupervisorReportDialog.tsx:21` and `src/shared/reports.ts:117` — The Summary report's "This Week" preset always runs Monday to Sunday (`getMonday`), and report "week" buckets always start on Sunday. Both ignore Settings → Week starts on, which the calendar, week view and requirements all follow. — Pass `weekStart` from the settings store or DB into both.
